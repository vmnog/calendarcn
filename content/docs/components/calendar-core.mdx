Calendar Core has no UI of its own. `CalendarProvider` holds the calendar's state (events, view, date, selection) and its settings, and `useCalendar()` reads and changes that state from any component inside it. Every view and the event details build on it. In the preview, the list on the right is the app's own `events` state: drag, resize or create an event and it updates.

## Usage

```tsx
import { CalendarProvider, useCalendar } from "@/components/calendar-provider";
import { WeekView } from "@/components/week-view";

export function Schedule() {
  return (
    <CalendarProvider defaultEvents={events}>
      <Toolbar />
      <WeekView />
    </CalendarProvider>
  );
}

function Toolbar() {
  const { monthName, year, goToPrev, goToNext } = useCalendar();
  // ...
}
```

### Controlled or uncontrolled

Each piece of state comes in a shadcn/Radix-style pair. Pass `defaultEvents` (or nothing) and the provider owns the events. Pass `events` with `onEventsChange` and your app owns them: the provider draws whatever `events` holds and reports every drag, resize, create and edit as the full next list. `view`, `date` and `numberOfDays` work the same way.

```tsx
const [events, setEvents] = React.useState(initialEvents);

<CalendarProvider events={events} onEventsChange={setEvents}>
  <WeekView />
</CalendarProvider>;
```

Use `onEventCreate`, `onEventUpdate`, `onEventDelete` and `onEventSelect` to react to one change at a time, for example to save it to a server. `onEventCreate` also gets an occurrence of a repeating event the first time it is edited: see [Repeating events](#repeating-events). To fetch events for the dates on screen as people navigate, use `onVisibleRangeChange` and `loading`: see [Loading Events](/docs/loading-events).

### Undo and redo

<KbdGroup>
  <Kbd>⌘</Kbd>
  <Kbd>Z</Kbd>
</KbdGroup>
takes back the calendar's own changes, newest first: creating, moving, resizing
and editing an event, and deleting, duplicating, cutting or pasting one.
<KbdGroup>
  <Kbd>⇧</Kbd>
  <Kbd>⌘</Kbd>
  <Kbd>Z</Kbd>
</KbdGroup>
does them again, until a new change clears what's left to redo. `undo()`,
`redo()`, `canUndo` and `canRedo` from `useCalendar()` do the same from your own
buttons. Edits to one event less than a second apart, like a title typed letter
by letter, are one step, and the provider keeps the last 100 steps.

Undo and redo report what they change like any other change: the full list through `onEventsChange`, then `onEventCreate`, `onEventUpdate` or `onEventDelete` for each event, so an app that saves one change at a time stays in sync. An undone delete adds the event back with its old id.

A step applies only while its events are the very objects the calendar left in `events`. Replace one from outside, by reloading your events from a server for example, and the steps that touch it can't be undone: `canUndo` turns false and the key goes back to the browser, so an undo never overwrites a newer version. Keep the objects you get in `onEventsChange`, as `useState` does, and undo keeps working. Changes your app makes to `events` itself, like an import, are not steps.

### Notices

After a delete, a cut or a copy, the provider keeps a notice worded like Notion Calendar's toasts: "Event deleted" with the event's title and an undo, "Event cut" with an undo, "Event copied to clipboard" with the title. [Calendar Toaster](/docs/components/calendar-toaster) shows it; without one, nothing shows. `useCalendarNotice()` returns it, to show with a toast library of your own, and `showNotice` adds notices of yours. A notice's undo takes back that action and nothing else, so the notice closes as soon as another change is the latest, and its undo is there exactly while `canUndo` is.

### Server rendering

Without `date` or `defaultDate`, the calendar starts on today's period. The server doesn't know the viewer's today or time zone, so in that case the provider renders nothing until hydration finishes, and server and client markup always match. Pass `defaultDate` to render on the server.

## Repeating events

An event with a `recurrenceRule` (or an RRULE in `recurrence`) is one event in `events`, and every view draws it on each date its rule gives, as does the details sidebar's search. The views generate those occurrences for the dates on screen with `expandRecurringEvents()`; they are never added to `events`, so `useCalendar().events`, `onEventsChange` and the .ics export hold each series once.

- An occurrence's id is the series' id and its date, `launch-2026-06-20`. Selecting it, `selectedEvent` and the details' series arrows work as for any event.
- Editing an occurrence (drag, resize, the keyboard or the details) changes that date only. It is added to your events with `seriesId` (the series' id) and `originalStart` (the start it had), through `onEventCreate` and `onEventsChange`, and drawn in place of the generated one. Later edits to it go through `onEventUpdate`. A new repeat rule takes it out of the series, to repeat on its own from its date.
- Editing the series' own event, its first date, changes the series: every occurrence you haven't stored follows it.
- Delete and Cut on one date leave it out of the series: its start is added to the series event's `excludedDates` (reported through `onEventUpdate`), and a stored date goes with it. The series' own event deletes the whole series. Undo and redo treat each as one step: the first edit of a generated date is a create, so undoing it brings the generated date back.
- Duplicate and Paste on a date of a repeating event add a single event on that date: the copy has no `seriesId`, `originalStart`, `recurrenceRule`, `recurrence` or `excludedDates`, so it doesn't repeat and the series keeps its dates.
- `excludedDates` leaves dates out, like an .ics `EXDATE`.
- Occurrences keep the series' clock time in its `timeZone` when the clocks change. An all-day series keeps whole days.
- `recurrence` written as display text ("Every week on Thu") is a label only: draw those occurrences as events of your own.

When you load events by range ([Loading Events](/docs/loading-events)), include the repeating events whose series reaches into the range, even when their first date is earlier.

## Configuration

<ComponentPreview name="config-demo" />

Display and interaction settings are plain props: a 24-hour clock, a [date-fns locale](https://date-fns.org/docs/I18n) for day and month names, the first day of the week, the visible hours of the time grid, and the minute step that drag, resize and click-to-create snap to. Events outside the visible hours are clipped at the edge, and hidden when they lie fully outside. Read the resolved settings anywhere with `useCalendarConfig()`, for example to format times in a custom renderer the way the calendar does.

### Time zone

<ComponentPreview name="time-zone-demo" />

By default the calendar draws in each viewer's own time zone. `timeZone` takes an IANA zone, like `"Asia/Tokyo"`, and draws the calendar on that zone's clock, as Notion Calendar's primary time zone: a team calendar in the office's zone, or a page your server renders the same for every visitor. Events sit at that zone's time, "today", the current-time line and the first day of each week follow it, a click on an empty slot creates the event at that row's time there, the details show times in it, and the time axis is labeled with it. In the preview the calendar is in Tokyo, with India's hours beside it, and "Your clock" lists the same events on your own clock.

```tsx
<CalendarProvider
  events={events}
  onEventsChange={setEvents}
  timeZone="Asia/Tokyo"
>
  <WeekView />
</CalendarProvider>
```

- What you pass in and get back stays instants: `events`, `onEventsChange`, `onEventCreate`, `onEventUpdate` and the range `createEvent` gets. `onVisibleRangeChange` gets the instants the days on screen start and end in that zone. Save and fetch as you do without it.
- Inside the provider, times read on the calendar's clock. Events from `useCalendar()`, `renderEventContent` and `renderEventDetails` are `Date`s whose local time (`getHours()`, date-fns `format()`) is that zone's, and `updateEvent` takes them the same way. `fromZonedWallClock(date, timeZone)` from `@/lib/time-zones`, with `timeZone` from `useCalendarConfig()`, turns one back into an instant. To expand repeating events yourself, pass that `timeZone` to `expandRecurringEvents()`.
- Days are calendar dates: `date`, `currentDate`, `visibleDays`, `useCalendar().visibleRange` and all-day events are local midnights whose year, month and day name the day.
- An event keeps its own `timeZone`, and one without it stays in the viewer's: a repeating meeting keeps its clock time there, and the details' time zone row shows that zone.
- `timeZone` is the primary zone, so it changes from the time axis labels and the command menu too: pass `onTimeZoneChange` with it, or `defaultTimeZone` to let the provider own it.
- A zone the runtime doesn't know is ignored, and the calendar draws in the viewer's.
- On the one night a year the viewer's own clocks skip an hour, a time in that hour can't be drawn: an event there is drawn from the hour after, and keeps its times when you edit something else.

### Additional time zones

<ComponentPreview name="secondary-time-zone-demo" />

`secondaryTimeZones` takes IANA time zones, like `["Asia/Kolkata"]`, and `secondaryTimeZone` one of them. The day and week views then show each zone's hours in a column left of the time axis, left to right, as Notion Calendar does with additional time zones. Each column has its zone's short label at the top, and the current-time line keeps its one time badge, in your column, as in Notion Calendar. A zone half an hour or 45 minutes off yours shows the minutes: beside your 10 AM, India's column reads 7:30 PM.

```tsx
<CalendarProvider defaultEvents={events} secondaryTimeZone="Asia/Kolkata">
  <WeekView />
</CalendarProvider>
```

People change the zones from the time axis, as in Notion Calendar:

- A click or right-click on a zone's label opens its menu: "Change time zone", "Make time zone primary" (or "Make time zone secondary" on the primary one) and "Remove time zone from list". The "+" left of "All-day" adds a zone, as the left-most column. Both lists search by city, zone name or offset ("+9", "GMT-3").
- The zones are provider state like `view`: pass `secondaryTimeZones` with `onSecondaryTimeZonesChange` to keep them in your app, or `defaultSecondaryTimeZones` to let the provider own them. `useCalendar().changeTimeZones()` changes them from your own controls, with the helpers in `@/lib/time-zones` (`addTimeZone`, `removeTimeZone`, `makeTimeZonePrimary`, `makeTimeZoneSecondary`, `replaceTimeZone`).

- The column shows one offset for every day on screen: the one at noon today while today is on screen, else at noon on the first day shown. In a week where either zone changes its clocks, it is off by that change on the days on the other side of it.
- Each column is 64px wide at every screen size, so on a phone the days get less room. To show them on wide screens only, pass the prop there.
- Screen readers read each zone's label once. Both columns' hours are hidden from them, like the time axis itself, since each event's label already reads its time.
- A zone the runtime doesn't know gets no column.
- [Calendar](/docs/components/calendar) and [Calendar App](/docs/components/calendar-app) take the props too. Calendar App's command menu adds one with "Show additional time zones...", and makes one primary or hides one with "Make time zone primary..." and "Hide time zone...".

### Travel to a time zone

Notion Calendar's "Travel to time zone" draws the calendar in another zone for a while, without changing your zones: the zone travelled to gets a column next to the days, filled in the primary color, with your home zone beside it. `useCalendar().travelToTimeZone(zone)` travels and `travelToTimeZone(null)` travels back; `travelTimeZone` is the zone travelled to, or `null` at home.

- In [Calendar App](/docs/components/calendar-app), <Kbd>Z</Kbd> or "Travel to time zone..." in the command menu lists the zones to travel to.
- The x on the travel label, "Travel back home" in its menu, and <Kbd>Esc</Kbd> with no event selected (with `useCalendarShortcuts()`) travel back. "Add as primary time zone" and "Add as secondary time zone" keep the zone.
- Travelling isn't saved: a reload starts at home.

## Meeting with people

`contacts` are also the people you can meet with, as in Notion Calendar's "Meet with...". `useCalendarPeople()` reads and changes who that is:

- **Meeting with someone** (`meetWith`, `addMeetWith`): their events are drawn in the day and week views behind yours, hatched in their color with their initial, and the times when you and everyone you meet with are free are highlighted, inside `workingHours` (9 AM to 5 PM, Monday to Friday by default) and at least 30 minutes long. An event created by clicking an empty slot meanwhile invites them: they're added to its `participants`, waiting for an answer, with the event's calendar account (`calendarEmail`) as the organizer.
- **Showing a teammate's calendar** (`teammates`, `addTeammate`): their events are drawn the same way, without a meeting: no free time, no invitations.

Their events come from `contactEvents`, keyed by email. Load them when someone is added (`onMeetWithChange`, `onTeammatesChange`) and when the dates on screen change (`onVisibleRangeChange`). From Google Calendar's free/busy API, which gives busy times without titles, pass an event titled "Busy" for each one. Repeating events work as yours do, and with [`timeZone`](#time-zone) or while travelling, their events and the working hours read on the calendar's clock, as yours do. All-day and multi-day events aren't drawn (an all-day event marked `status: "busy"` still takes the day out of the free time), and month, year and agenda views leave other people's events out.

```tsx
const [meetWith, setMeetWith] = React.useState<string[]>([]);
const contactEvents = useFreeBusy(meetWith, visibleRange); // your loader

<CalendarProvider
  defaultEvents={events}
  contacts={contacts}
  meetWith={meetWith}
  onMeetWithChange={setMeetWith}
  contactEvents={contactEvents}
>
  <CalendarSidebar />
  <WeekView />
</CalendarProvider>;
```

The [Calendar Sidebar](/docs/components/calendar-sidebar)'s "Meet with..." field and the [People Picker](/docs/components/people-picker) (F and P in [Calendar App](/docs/components/calendar-app)) add people; your own controls can call `addMeetWith`, `addTeammate` and the rest. `getSharedFreeTime(calendars, days, options)` in `lib/free-busy.ts` computes the highlighted free time, to list it elsewhere: it counts an event as busy unless it's marked `status: "free"`, the calendar's owner declined it, or it's all-day (unless marked busy).

## Custom event content

<ComponentPreview name="custom-event-content-demo" />

`renderEventContent` replaces what's drawn inside each event. The calendar keeps drawing the box (position, color, selection, drag and resize handles), so the renderer only returns the inside. `placement` says where the event is drawn and how much room it has: a timed block in the hour grid (`"time-grid"`, as tall as the event), a 24px bar in the all-day row (`"all-day"`), a 20px line in month view (`"month-item"` and `"month-bar"`), or a row as wide as the [agenda](/docs/components/agenda-view) (`"agenda"`). `isCompact` is true wherever there's room for one line only.

To replace the details popover instead, see [Event Details](/docs/components/event-details#custom-details).

## Typed events

<ComponentPreview name="typed-events-demo" />

Extend `CalendarEvent` with your own fields and pass your events in. The provider infers your type, and every callback and renderer gets it back. Read it in your own components with `useCalendar<Meeting>()`.

Once your type has required fields, `createEvent` becomes required: the calendar can't fill `room` or `attendees` for an event created by clicking an empty slot, so TypeScript asks you to.

```tsx
interface Meeting extends CalendarEvent {
  room: string;
  attendees: string[];
}

<CalendarProvider
  defaultEvents={meetings}
  createEvent={(range) => ({
    id: crypto.randomUUID(),
    title: "New meeting",
    ...range,
    room: "Atlas",
    attendees: [],
  })}
>
  <WeekView />
</CalendarProvider>;
```

### useCalendar()

### ConferenceProviderOption

An entry of the `conferenceProviders` prop: one item of the Conferencing menu. None is on by default and none carries a service's brand: pass your own logos through `icon`. [`@calendarcn/conference-providers`](/docs/components/event-details#conference-providers) has placeholder Google Meet, Zoom and Microsoft Teams options to start from.

```tsx
const conferenceProviders: ConferenceProviderOption[] = [
  {
    provider: "zoom",
    label: "Zoom",
    icon: <ZoomIcon />,
    // Your server asks Zoom for a meeting
    createConference: async (event) => {
      const meeting = await createZoomMeeting(event.title);
      return { provider: "zoom", url: meeting.joinUrl, meetingId: meeting.id };
    },
  },
];

<CalendarProvider conferenceProviders={conferenceProviders}>
  <WeekView />
</CalendarProvider>;
```
