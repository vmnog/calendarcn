Calendar Core has no UI of its own. `CalendarProvider` holds the calendar's state (events, view, date, selection) and its settings, and `useCalendar()` reads and changes that state from any component inside it. Every view and the event details build on it. In the preview, the list on the right is the app's own `events` state: drag, resize or create an event and it updates.

## Installation

## Usage

```tsx
import { CalendarProvider, useCalendar } from "@/components/calendar-provider";
import { WeekView } from "@/components/week-view";

export function Schedule() {
  return (
    <CalendarProvider defaultEvents={events}>
      <Toolbar />
      <WeekView />
    </CalendarProvider>
  );
}

function Toolbar() {
  const { monthName, year, goToPrev, goToNext } = useCalendar();
  // ...
}
```

### Controlled or uncontrolled

Each piece of state comes in a shadcn/Radix-style pair. Pass `defaultEvents` (or nothing) and the provider owns the events. Pass `events` with `onEventsChange` and your app owns them: the provider draws whatever `events` holds and reports every drag, resize, create and edit as the full next list. `view`, `date` and `numberOfDays` work the same way.

```tsx
const [events, setEvents] = React.useState(initialEvents);

<CalendarProvider events={events} onEventsChange={setEvents}>
  <WeekView />
</CalendarProvider>;
```

Use `onEventCreate`, `onEventUpdate`, `onEventDelete` and `onEventSelect` to react to one change at a time, for example to save it to a server. `onEventCreate` also gets an occurrence of a repeating event the first time it is edited: see [Repeating events](#repeating-events). To fetch events for the dates on screen as people navigate, use `onVisibleRangeChange` and `loading`: see [Loading Events](/docs/loading-events).

### Undo and redo

<KbdGroup>
  <Kbd>⌘</Kbd>
  <Kbd>Z</Kbd>
</KbdGroup>
takes back the calendar's own changes, newest first: creating, moving, resizing
and editing an event, and deleting, duplicating, cutting or pasting one.
<KbdGroup>
  <Kbd>⇧</Kbd>
  <Kbd>⌘</Kbd>
  <Kbd>Z</Kbd>
</KbdGroup>
does them again, until a new change clears what's left to redo. `undo()`,
`redo()`, `canUndo` and `canRedo` from `useCalendar()` do the same from your own
buttons. Edits to one event less than a second apart, like a title typed letter
by letter, are one step, and the provider keeps the last 100 steps.

Undo and redo report what they change like any other change: the full list through `onEventsChange`, then `onEventCreate`, `onEventUpdate` or `onEventDelete` for each event, so an app that saves one change at a time stays in sync. An undone delete adds the event back with its old id.

A step applies only while its events are the very objects the calendar left in `events`. Replace one from outside, by reloading your events from a server for example, and the steps that touch it can't be undone: `canUndo` turns false and the key goes back to the browser, so an undo never overwrites a newer version. Keep the objects you get in `onEventsChange`, as `useState` does, and undo keeps working. Changes your app makes to `events` itself, like an import, are not steps.

### Notices

After a delete, a cut or a copy, the provider keeps a notice worded like Notion Calendar's toasts: "Event deleted" with the event's title and an undo, "Event cut" with an undo, "Event copied to clipboard" with the title. [Calendar Toaster](/docs/components/calendar-toaster) shows it; without one, nothing shows. `useCalendarNotice()` returns it, to show with a toast library of your own, and `showNotice` adds notices of yours. A notice's undo takes back that action and nothing else, so the notice closes as soon as another change is the latest, and its undo is there exactly while `canUndo` is.

### Server rendering

Without `date` or `defaultDate`, the calendar starts on today's period. The server doesn't know the viewer's today or time zone, so in that case the provider renders nothing until hydration finishes, and server and client markup always match. Pass `defaultDate` to render on the server.

## Repeating events

An event with a `recurrenceRule` (or an RRULE in `recurrence`) is one event in `events`, and every view draws it on each date its rule gives, as does the details sidebar's search. The views generate those occurrences for the dates on screen with `expandRecurringEvents()`; they are never added to `events`, so `useCalendar().events`, `onEventsChange` and the .ics export hold each series once.

- An occurrence's id is the series' id and its date, `launch-2026-06-20`. Selecting it, `selectedEvent` and the details' series arrows work as for any event.
- Editing or deleting one date (drag, resize, the keyboard, the right-click menu or the details) asks which events it applies to: see [Editing a repeating event](#editing-a-repeating-event). **This event** changes that date only. It is added to your events with `seriesId` (the series' id) and `originalStart` (the start it had), through `onEventCreate` and `onEventsChange`, and drawn in place of the generated one. Later edits to it go through `onEventUpdate`.
- Cut on one date, and Delete with **This event**, leave it out of the series: its start is added to the series event's `excludedDates` (reported through `onEventUpdate`), and a stored date goes with it. Cut on the series' own event cuts the whole series. Undo and redo treat each as one step: the first edit of a generated date is a create, so undoing it brings the generated date back.
- Duplicate and Paste on a date of a repeating event add a single event on that date: the copy has no `seriesId`, `originalStart`, `recurrenceRule`, `recurrence` or `excludedDates`, so it doesn't repeat and the series keeps its dates.
- `excludedDates` leaves dates out, like an .ics `EXDATE`.
- Occurrences keep the series' clock time in its `timeZone` when the clocks change. An all-day series keeps whole days.
- `recurrence` written as display text ("Every week on Thu") is a label only: draw those occurrences as events of your own.

When you load events by range ([Loading Events](/docs/loading-events)), include the repeating events whose series reaches into the range, even when their first date is earlier.

### Editing a repeating event

A change to one date of a repeating event asks which events it applies to, as Notion Calendar does: **This event**, **This and following events** or **All events** (on the series' first date, only this event or all events; a repeat rule change, only the following or all events). A drag, a resize, an <Kbd>Alt</Kbd> arrow move or a change from the right-click menu asks at once. A change in the details waits: the date shows it on the calendar with a dot before its title, and the question comes when you leave the event, listing what changed. **Save event** applies it, **Discard change** drops it, **Continue editing** goes back to it, and so does <Kbd>Esc</Kbd>. A delete asks the same way, with **Delete event** and **Cancel**.

- **This event** stores the date as an event of its own (with `seriesId` and `originalStart`), or, for a delete, adds its start to the series' `excludedDates`.
- **This and following events** ends the series the day before (its `end` becomes that date) and starts a new series event, with a new id, from this date. A series that ends after a number of times keeps the count that's left. Later dates stored on their own move to the new series.
- **All events** changes the series event. A new time moves every date; dates with a time of their own keep it. Deleting all events deletes the series and its stored dates.

When a date moves to another day, or the repeat rule changes, the stored dates and excluded dates it affects are removed: their days are no longer in the series.

Each answer is one undo step. `onEventsChange` gets the full list once, then `onEventDelete`, `onEventUpdate` and `onEventCreate` get each event the answer removed, changed or added, in that order, so a new series reaches your server before its dates. A change that waits is never reported. After an answer, a toast says what happened: Event deleted, All events deleted (both with Undo) or Event updated.

The views render the question with `EventSeriesScopeDialog` (`@/components/event-series-scope-dialog`). In a layout without them, render it once inside the provider; without it, a change applies to that date only (a repeat rule change, to that date and the following ones). To skip the question in your own code, pass the answer: `updateEvent(event, "all")` or `deleteEvent(event.id, "this")`. Custom details should change events with `editEvent(event)`, which waits like the built-in details. `getSeriesEditChanges()` and `getSeriesDeleteChanges()` from `@/lib/recurrence` return the same changes without a provider.

## Configuration

<ComponentPreview name="config-demo" />

Display and interaction settings are plain props: a 24-hour clock, a [date-fns locale](https://date-fns.org/docs/I18n) for day and month names, the first day of the week, the visible hours of the time grid, and the minute step that drag, resize and click-to-create snap to. Events outside the visible hours are clipped at the edge, and hidden when they lie fully outside. Read the resolved settings anywhere with `useCalendarConfig()`, for example to format times in a custom renderer the way the calendar does.

### Second time zone

<ComponentPreview name="secondary-time-zone-demo" />

`secondaryTimeZone` takes an IANA time zone, like `"Asia/Kolkata"`. The day and week views then show its hours in a second column left of the time axis, as Notion Calendar does with an additional time zone. Each column has its zone's short label at the top, and the current-time line keeps its one time badge, in your column, as in Notion Calendar. A zone half an hour or 45 minutes off yours shows the minutes: beside your 10 AM, India's column reads 7:30 PM.

```tsx
<CalendarProvider defaultEvents={events} secondaryTimeZone="Asia/Kolkata">
  <WeekView />
</CalendarProvider>
```

- The column shows one offset for every day on screen: the one at noon today while today is on screen, else at noon on the first day shown. In a week where either zone changes its clocks, it is off by that change on the days on the other side of it.
- The column is 64px wide at every screen size, so on a phone the days get less room. To show it on wide screens only, pass the prop there.
- Screen readers read each zone's label once. Both columns' hours are hidden from them, like the time axis itself, since each event's label already reads its time.
- A zone the runtime doesn't know shows no second column.
- [Calendar](/docs/components/calendar) and [Calendar App](/docs/components/calendar-app) take the prop too. Calendar App has no control to pick the zone yet: "Show additional time zones..." in its command menu is still marked Soon.

## Custom event content

<ComponentPreview name="custom-event-content-demo" />

`renderEventContent` replaces what's drawn inside each event. The calendar keeps drawing the box (position, color, selection, drag and resize handles), so the renderer only returns the inside. `placement` says where the event is drawn and how much room it has: a timed block in the hour grid (`"time-grid"`, as tall as the event), a 24px bar in the all-day row (`"all-day"`), a 20px line in month view (`"month-item"` and `"month-bar"`), or a row as wide as the [agenda](/docs/components/agenda-view) (`"agenda"`). `isCompact` is true wherever there's room for one line only.

To replace the details popover instead, see [Event Details](/docs/components/event-details#custom-details).

## Typed events

<ComponentPreview name="typed-events-demo" />

Extend `CalendarEvent` with your own fields and pass your events in. The provider infers your type, and every callback and renderer gets it back. Read it in your own components with `useCalendar<Meeting>()`.

Once your type has required fields, `createEvent` becomes required: the calendar can't fill `room` or `attendees` for an event created by clicking an empty slot, so TypeScript asks you to.

```tsx
interface Meeting extends CalendarEvent {
  room: string;
  attendees: string[];
}

<CalendarProvider
  defaultEvents={meetings}
  createEvent={(range) => ({
    id: crypto.randomUUID(),
    title: "New meeting",
    ...range,
    room: "Atlas",
    attendees: [],
  })}
>
  <WeekView />
</CalendarProvider>;
```
