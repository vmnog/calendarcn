# src/components/ — Local Context

## What Lives Here

All React components for CalendarCN. Split into:

- `ui/` — shadcn/ui primitives (don't edit directly)
- `calendar-provider.tsx` — `CalendarProvider` / `useCalendar()`: state, navigation, view sync
- `time-grid.tsx` — `TimeGrid`, the hourly grid for day and week (`view` prop); `day-view.tsx` and `week-view.tsx` are one-line wrappers that fix `view`
- `week-view-*.tsx` — the time grid's parts (all-day row, grid, time axis, now line)
- `month-view*.tsx` — `MonthView` and its parts
- `agenda-view.tsx` — `AgendaView`, a list of the next `AGENDA_DAYS` days' events grouped by day
- `calendar-event-*` / `event-*` — event interactions
- `calendar-sidebar.tsx` — the left sidebar (`CalendarSidebar`): `mini-calendar.tsx`, `calendar-list.tsx`, `theme-toggle.tsx`
- `details-sidebar.tsx` — the right context panel (`DetailsSidebar`): details, search, shortcuts
- `sidebar-overlay.tsx` — both sidebars as a sheet on narrow screens, and `CALENDAR_SIDEBAR_COLORS_CLASS`, which maps `--sidebar-*` to the `--calendar-sidebar-*` tokens

## Gotchas

### Type Definitions

**All shared types live in `week-view-types.ts`** — the canonical source. Never define types inline in component files unless they're truly local (used only in that file). When in doubt, put it in `week-view-types.ts`.

### View Sync

Every view reports what it draws with `useCalendarViewSync().reportView(...)` from a layout effect (TimeGrid: its `view` and fixed `numberOfDays`; MonthView: `"month"`; AgendaView: `"agenda"`). The provider adopts it while `view` is uncontrolled and undoes switches the mounted view doesn't follow (full rule in the `CalendarProvider` JSDoc). For the commit before the provider adopts a view, `isProviderInSync` is false: skip slide animations and `reportVisibleDays` / `reportDisplayMonth` then, since the date change is the adoption, not navigation. A new view must follow the same pattern.

### Event Color Styling

Never hardcode color classes. Always use the `eventColorStyles[color]` map from `calendar-event-item.tsx`. The map returns `{ bg, bgHover, border, borderLine, text }` CSS class strings.

### Multi-Day Event Segments

A multi-day event renders as multiple `CalendarEventItem` instances, one per day. Each gets a `segmentPosition`:

- `"full"` — single-day event (all corners rounded)
- `"start"` — first day of multi-day (left corners rounded)
- `"middle"` — interior day (no rounded corners)
- `"end"` — last day of multi-day (right corners rounded)

Don't assume an event item represents the whole event. Always check `segmentPosition`.

### Z-Index

Follow the strict z-index scale. If you add a new layer, check it doesn't conflict:

- Events: `0–2` (column index)
- Selected: `20`
- Placeholder: `25`
- Dragging: `30`
- Portal: `9999`

### Accessibility

- Every interactive event element gets `data-event-id`, `aria-label` from `getEventLabel()` (locale and `hourCycle` aware) and `aria-pressed` for selection. Keyboard move/resize (`useEventKeyboard`) and focus restoration find events by `data-event-id`, so drag visuals (ghosts, placeholders, floating copies, resize previews) must not carry it, and must be `aria-hidden`.
- Off-screen scroll buffer columns (week) and rows (month) are `inert`: never tabbable, never read out.
- Focus rings use `EVENT_FOCUS_RING_CLASS` (a `focus-visible` `::after` border). An `outline` or `box-shadow` ring is painted under the events' absolutely positioned background layers.
- Time changes are announced by the provider's live region from `updateEvent`/`addEventFromRange`; don't announce from components.

### shadcn/ui Components

Files in `ui/` are generated by `shadcn`. Customize behavior by wrapping or extending in a new component — don't modify `ui/` files directly. They'll be overwritten on `shadcn` updates.

### Registry Files

Every file listed in `registry.json` ships to other projects through `npx shadcn add @calendarcn/<item>`, where it runs against the user's own stock shadcn/ui components, Radix or Base UI. In those files, use only the stock `ui/*` API: no repo-only variants like `Kbd variant` or `Switch size="xs"` (use classes instead). Keep to what both libraries share: `asChild` only around a JSX element written in place (the CLI turns it into Base UI's `render`, but drops it around a variable), `onClick` rather than `onSelect` on menu items, no `PopoverAnchor` or Radix-only content props, and both `data-[state=checked]:` and `data-checked:` for checked styles. The event details popover renders its own floating layer for this reason. After changing one, or adding a file an item needs, run `pnpm registry:build` and commit `public/r`.
